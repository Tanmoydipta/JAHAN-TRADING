4. EXE BUILD ISSUE — DIAGNOSED & FIXED
================================================================================
Problem: User reported "nothing happens" when double-clicking the built .exe.

Diagnosis:
   - Ran the exe directly from terminal to capture console output
   - Found: ModuleNotFoundError: No module named 'flask'
   - Root cause: machine has two Python installs (3.12 and 3.14). Flask +
     PyInstaller were installed under Python 3.14, but the bare `pyinstaller`
     command on PATH resolved to the Python 3.12 copy (which has no Flask).
     PyInstaller silently bundled without Flask, exe crashed instantly.

Fix:
   - Rebuilt manually using `C:\Python314\python.exe -m PyInstaller ...`
   - Verified: exe now boots cleanly, Flask server starts, DB initializes
   - Patched build.py: changed hardcoded `"pyinstaller"` command to use
     `sys.executable -m PyInstaller` — this guarantees future builds always
     use whichever Python interpreter runs build.py (avoids the PATH
     mismatch permanently)
   - Re-verified: `C:\Python314\python.exe build.py` now builds correctly
     end-to-end

Also cleaned up: deleted a stale standalone dist/JahanTradingSystem.exe
(16MB, old --onefile build with the OLD pre-rewrite schema) per user request,
to avoid confusion with the current --onedir build in
dist/JahanTradingSystem/JahanTradingSystem.exe.

5. CLOUD DATABASE RESEARCH & RECOMMENDATION
================================================================================
User asked about moving the database to the cloud.

Key finding: database.py already supports MySQL mode via pymysql — switching
database_config.mode to "mysql" and filling host/port/user/password/database
in config.json works with zero code changes to the schema logic.

Efficiency note flagged: current code opens a fresh DB connection per API
request (no pooling) — fine for local SQLite, but adds latency over a real
network connection to a cloud MySQL server. Recommended adding connection
pooling (e.g. DBUtils.PooledDB) if performance matters at cloud scale.

Discussed Oracle Cloud Free Tier: clarified their free database is Oracle
Autonomous DB (not MySQL) — would require rewriting the DB layer for Oracle's
driver/dialect. Alternative: self-host MySQL on Oracle's free compute VM
(zero-cost forever, but you own patching/backups/security).

Researched (via WebSearch) current 2026 pricing for managed MySQL providers:
   - Aiven Free Tier: $0/mo, 1GB storage/1GB RAM, single-node, fully managed,
     no credit card required, but auto-sleeps after inactivity — best starting
     point for a low-traffic app
   - DigitalOcean Managed MySQL: $15/mo flat, predictable, always-on,
     recommended upgrade path once free tier limits are hit
   - Railway: usage-based billing, unpredictable, typically $20–50/mo real
     cost — not recommended for this use case
   - AWS RDS/Aurora, Azure, Google Cloud SQL: overkill complexity/cost for a
     single-branch trading app — not recommended

Recommendation given: start on Aiven free tier, upgrade to DigitalOcean $15/mo
if/when the free tier's sleep behavior or 1GB cap becomes limiting.

   - User downloaded Aiven's CA certificate into the project root as ca.pem
     (1541 bytes)

SSL BUG — diagnosed and fixed in database.py get_db_connection():
   - Initial attempt: pymysql.connect(ssl={'ca': resolved_ca}) (the simple
     dict-shortcut form) FAILED against Aiven with:
     ssl.SSLCertVerificationError: CERTIFICATE_VERIFY_FAILED: self-signed
     certificate in certificate chain
   - Root cause: Aiven's CA is a private/self-signed root; PyMySQL's dict
     shortcut doesn't reliably combine hostname verification with a
     self-signed trust anchor.
   - Fix: build an explicit ssl.SSLContext instead —
     ssl.create_default_context(cafile=resolved_ca), then
     check_hostname=False, verify_mode=ssl.CERT_REQUIRED, and pass that
     context object directly as connect_kwargs['ssl']. This is now the
     permanent, correct pattern in database.py — do not revert to the dict
     shortcut.
   - Verified live: "Connected! Mode: mysql", "MySQL version: 8.4.8", all 7
     tables created on defaultdb, admin user + demo products seeded on Aiven
     itself (confirmed directly via `mysql` CLI client against Aiven too).

SECURITY FIX (found proactively during testing, not reported by user):
   - /api/config in app.py was returning the FULL database_config object,
     including the live plaintext Aiven password, to any client that hit the
     endpoint.
   - Fixed: api_get_config() now strips database_config down to just
     {"mode": "mysql"} before returning it. Full password/host/user never
     leave the server to the browser. This must not be reverted.
   - While testing the fix, found multiple stale python.exe processes from
     earlier test runs still bound to port 5000, serving old unpatched code
     (pkill hadn't actually killed them). Resolved via
     `netstat -ano | grep :5000` to find PIDs, then
     `taskkill //F //PID <pid> //T` to force-kill each (with child processes).
     Restarted cleanly and reconfirmed the fix took effect.

8. "FAILED TO FETCH" INCIDENT — DIAGNOSED
================================================================================
User reported browser error "Connection failure: Failed to fetch" (this
string comes from static/app.js's handleFormSubmit() catch block:
alert("Connection failure: " + err.message)).

Diagnosis: ran `netstat -ano | grep ":5000"` and `tasklist` filters for both
JahanTradingSystem.exe and python.exe — found NOTHING listening on port 5000
and no matching process running at all. Conclusion: the server simply was
not running (exe/console window had been closed, or the dev instance had
been killed/crashed) — nothing exotic, no code bug. "Failed to fetch" is the
browser's generic error when fetch() can't reach a server at all.

Resolution given to user: relaunch
dist/JahanTradingSystem/JahanTradingSystem.exe and keep its console window
open while using the app (closing that window kills the Flask server).
Noted Aiven free-tier auto-sleep as a possible contributor to a slow first
request after idle time, but the primary cause was simply "no server
process running."
